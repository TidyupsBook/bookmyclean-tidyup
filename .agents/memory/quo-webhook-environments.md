---
name: Quo webhooks across environments
description: One shared Quo account serves dev and prod; what a line re-pick actually deletes and what is safe to clean up
---

The Quo workspace (phone account) is shared by dev and prod, but webhook registrations are tracked per-environment in each env's own `quo_webhooks` table. Re-picking lines (`POST /api/quo/numbers`) registers a fresh 4-hook set at that environment's `publicWebhookUrl()` and deletes only the ids stored in its own DB.

**Why it matters:** strays accumulate on Quo's side. Observed 2026-08-08: five enabled `bookmycleaning-7-*` sets at the prod URL plus one dev-domain set — only one set's signing keys are known to prod, so the others fail signature verification on every delivery (noise, and persistent-failure risk of Quo auto-disabling hooks; per-delivery idempotency prevents double-processing, so it is not a correctness bug). A dev re-pick pointing a set at the sleeping workspace is harmless duplication — but if an environment's DB was cloned from prod, its stored "previous" ids can be another environment's LIVE hooks, and the delete step then severs prod ingestion.

**How to apply:** before blaming code for missing call events, compare `quo_webhooks` rows in dev and prod DBs against `quo.listWebhooks(apiKey)`. Only delete `bookmycleaning-*` hooks whose URL host belongs to the environment doing the deleting; never touch Make.com hooks or another host's registrations. As of 2026-08-08 this ownership rule is enforced in code (`ownsWebhookHost` guard at every delete site: boot reconcile, line re-pick, disconnect), so cloned rows are re-registered without killing the other env's hooks.

**Resolution of the 2026-08 dead-ingestion incident:** the cross-env deletes were only half the story. The bigger killer was the webhook age gate: Quo retries failed deliveries for hours **with the original `webhook-timestamp`**, so a 5-minute stale gate permanently rejected every delivery that missed its first attempt (sleeping/redeploying server) — an entire retry backlog 401'd silently, with no signature-failure warns because rejection happened pre-signature. Claim-row idempotency already provides replay protection, so the gate is now 48h, ms-format timestamps are tolerated, and both pre-signature 401 branches warn-log why. Also: the workspace `QUO_API_KEY` secret is dead (401s) — the live keys are the per-company encrypted ones in the companies table. Quo has no test-fire endpoint; verify with a signed self-test POST (marked `selftest.*`) — and remember a 200 in the request log may be your own self-test, so confirm via `quo_webhook_deliveries` rows before declaring real traffic ingested.
